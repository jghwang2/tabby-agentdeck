## 1. [P1] 파일 경로 추출이 경로 없는 긴 문자열에서 UI를 막는다

**위치:** `src/viewer.ts:93`, `src/viewer.ts:113`, `src/viewPanel.ts:997`.

`PATH_RE`는 시작 경계 없이 문자열의 각 위치에서 긴 문자 반복을 소비한 뒤 확장자를 찾는다. `a`처럼 경로 문자에 해당하지만 점이 없는 긴 출력은 매 시작 위치에서 실패하고 다시 탐색한다. 16KB 상한이 있어도 400ms 주기 UI 처리에 과도한 비용이다. 패널이 닫혀 있어도 `noteOutput → scrape → extractPaths`가 실행된다.

**재현:** 실제 소스를 임시 transpile하여 `extractPaths('a'.repeat(n))` 실행. 2KB 18.64ms, 4KB 81.84ms, 8KB 327.54ms, 16KB 964.12ms. 별도 격리 Tabby에서 실제 `ViewPanel.noteOutput`에 16KB를 전달했을 때, 패널이 닫힌 상태에서도 UI 타이머가 **614.4ms** 지연됐다. 합성 입력이며, 일반 모든 출력에 동일 비용이 난다는 뜻은 아니다.

**수정 방향:** 경로 후보 토큰을 선형으로 나누고 점/구분자 유무를 먼저 확인한 뒤, 토큰 전체에 고정된 패턴으로 검증한다. 같은 문자열의 모든 접미사에 재시도하지 않도록 한다. 한글/Windows/상대경로와 기존 오탐 배제 규칙은 유지해야 한다.

## 2. [P1] 미리보기의 읽기 상한이 실제 파일 읽기에 적용되지 않는다

**위치:** `src/viewPanel.ts:223`, `src/viewPanel.ts:224`, `src/viewPanel.ts:261`, 호출 `:1416`, `:1434`, `:1456`.

`readTextHead`는 `fs.readFileSync(file)`로 전체 파일을 할당한 뒤 `buf.slice(0, limit)`한다. 표시 상한 1,500,000바이트는 I/O·메모리 상한이 아니다. 큰 로그/CSV를 열거나 자동 따라가기로 선택하면 파일 전체 크기만큼 UI 동기 읽기 및 Buffer 할당이 발생한다. 편집용 `readTextAll`도 전체를 읽은 뒤 크기를 거절한다.

**재현:** 원본 함수 본문을 추출해 64MiB 임시 파일로 시험. 실제 읽기 **67,108,864바이트**, 반환 **1,500,000문자**, `truncated=true`, 소요 28.19ms. 이 시간은 로컬 캐시 조건 수치이며, 핵심은 입력 크기가 무제한으로 읽힌다는 점이다. 수GB 파일 시험이나 실제 OOM을 일으키지는 않았다.

**수정 방향:** 열린 핸들의 크기를 확인하고 앞부분만 제한해 읽는다. 편집은 파일 크기 확인 후 제한 초과면 읽기 전에 거절하고, 검사 이후 파일 성장도 읽기 한도로 방어한다. 가능하면 비동기로 실행한다.

## 3. [P2] Codex 메타 스캔이 초기 기록 전체를 UI에서 동기 처리한다

**위치:** `src/notify.service.ts:1415`, `:1452`, `src/codexMeta.ts:feedCodexChunk`.

`len = size - scan.lastSize`를 그대로 Buffer에 할당하고 `readSync → 문자열 변환 → split → JSON.parse`를 한 번에 실행한다. 첫 연결/재시작에서는 `lastSize=0`이므로 큰 기록 전체가 대상이다. 여러 탭은 한 타이머 콜백에서 순차 처리한다. 관련 없는 대화 출력 레코드도 JSON 파싱을 통과한다.

**재현:** 실제 `feedCodexChunk`에 합성 일반 응답 기록을 전달했을 때 8MiB 26.56ms, 32MiB 86.13ms, 64MiB **187.26ms**. 파일 읽기·디코딩을 제외한 파싱만의 시간이다. 실사용 기록의 전체 스캔 지연을 측정한 것은 아니다.

**수정 방향:** 청크별 바이트/시간 예산과 이벤트 루프 양보를 적용하거나 worker로 옮긴다. 같은 파일의 `scanSubagents → readGrowth`는 비동기 스트림과 중복 실행 방지가 이미 있어 비교 기준으로 삼을 수 있다. 비동기 읽기만으로 대규모 파싱까지 자동 해결되지는 않는다.

## 4. [P2] 같은 PTY 출력에 상태 분석을 중복 실행한다

**위치:** `src/decorator.ts:59`, `src/deck.service.ts:1904`, `src/detect.ts:163`, `:170`.

Decorator와 서비스 워처가 같은 pane/session의 출력을 각각 `applyOutput`에 전달한다. 구형 복구 누락을 보완하려는 의도는 주석에 있으나, 둘 다 정상 연결된 경우의 단일 소유권/중복 차단이 없다. 각 분석 안에서도 승인 패턴은 별도 판별과 waitingPatterns에 들어가 비매치 출력을 반복 검사한다. 상태가 멱등이어도 문자열 분석 비용은 멱등이 아니다.

**실측:** 앞선 격리 시험에서 단일 합성 출력 덩어리에 동일 승인 정규식이 **4회** 실행됐다. 총 30.40초 중 30.39초가 이 네 검사였다. 특정 pane의 중복 바인딩이 무한히 누적된다는 주장까지 검증한 것은 아니다.

**수정 방향:** session/pane 단위로 출력 분석 소유자를 하나로 정하고 복구 경로는 누락 시에만 연결한다. ANSI 정리와 승인 검사 결과를 같은 처리 안에서 재사용한다. 청크 경계의 누적 버퍼와 정확한 agent profile을 유지해야 한다.

## 5. [P2] 접힌 지난 세션 목록이 전체 디렉터리 스캔을 계속 유발한다

**위치:** `src/deck.service.ts:4586`, `:5082`, `:5120`, `src/sessionLedger.service.ts:153`, `:scan`.

기본 매초 tick이 `render`를 실행하고, `renderResumeDrawer`는 펼침 여부를 검사하기 전에 `ledger.refresh()`를 호출한다. refresh의 15초 제한은 중복 실행 빈도만 줄이며, 접힌 상태에서의 주기적 전체 스캔을 막지 않는다. scan은 Claude 프로젝트와 Codex 날짜 디렉터리를 돌며 파일 stat을 수행한다. 앞부분 200개 상한은 디렉터리 탐색·stat 이후에 적용된다. '목록을 펼칠 때와 탭이 닫힐 때만 스캔'이라는 주석과 실행 경로가 다르다.

**확실도:** 정적 호출 경로 확인. 실제 전체 사용자 기록을 반복 스캔하는 부하 시험은 하지 않았다.

**수정 방향:** 열기/닫기/새 기록 도착 이벤트로 갱신을 예약하고, 접힌 상태의 초 단위 렌더와 디스크 스캔을 분리한다. 목록이 열려 있더라도 내용이 같으면 전체 행 DOM을 매초 다시 만들지 않는다. 결과 건수를 잘라 기능을 축소하는 해결은 필요 없다.

## 6. [P2] Codex와 훅 기반 탭에서도 Claude 기록 폴백을 찾는다

**위치:** `src/notify.service.ts:1721`, `:1747`, `:1818`; 결과 사용처 `:1636`.

`scanSubagents`는 모든 sessionTab에 대해 Claude projects 경로의 `findTranscript`를 호출한다. Codex 여부나 `agentHookSeen`을 걸러내지 않는다. 그런데 `subagentsOf`는 훅이 확인된 탭이면 이미 훅 결과를 우선 반환해 폴백 집계를 사용하지 않는다. Codex 세션은 일반적으로 Claude 기록에서 찾지 못하므로 10초 재탐색 제한마다 디렉터리 순회를 반복할 수 있다.

**재현:** 원본 메서드를 추출한 호출 시험에서 `hookAgent=codex`, `agentHookSeen=true`인 탭도 Claude 기록 조회를 1회 요청했다. 디렉터리 전체 순회 시간을 실측한 시험은 아니다.

**수정 방향:** 폴백이 실제 필요한 provider/세션만 스캔한다. authoritative hook으로 전환되면 기존 폴백 스캔도 중지·정리한다.

## 7. [P2] 변경 없는 상태·메타 파일을 400ms마다 동기 재독한다

**위치:** `src/notify.service.ts:640`, `:1028`, `:1374`.

`poll`과 `pollMeta`는 먼저 디렉터리 전체 JSON을 readFileSync/JSON.parse한 뒤 메모리의 ts와 비교한다. 중복 적용은 차단하지만 파일 읽기와 파싱은 그대로 반복된다. 계정/세션 수가 늘수록 UI 콜백의 동기 작업도 증가한다.

**재현:** 원본 pollMeta 본문, 고정된 메타 파일 10개, 25회 호출 시험에서 readdir **25회**, readFile **250회**. 400ms 주기로 환산하면 10초 분량이다. 목 파일시스템 호출 횟수 시험이며 실제 디스크 250회 측정과 구분한다. 상태 폴더는 별도로 추가된다.

**수정 방향:** 파일 변경 알림 또는 비동기 stat 기반 변경 캐시를 두고 변경분만 읽는다. 훅의 원자적 파일 교체, 동시 쓰기, 놓친 이벤트를 복구할 저빈도 재스캔도 고려한다.
